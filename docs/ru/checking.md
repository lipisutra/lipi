# Проверки проекта

Режимы, уровни и история проверок. Общие принципы — в [правилах](rules.md).

| Режим | Когда | Чем кончается |
| --- | --- | --- |
| Быстрый | `lipi check`; на каждый коммит — только при `"enforce": true`; в CI — если он подключён | находки с кодом 0, 1 или 2; блокирует коммит только строгость, выбранная проектом |
| Аудит | вручную: перед сложной или ответственной задачей и после неё, перед выпуском | список для разбора |

Строгость — выбор проекта (ADR-011): ключ `enforce` в `lipi.json`, по
умолчанию `false`. При `false` lipi не ставит pre-commit, а поставленный им
раньше `lipi init` убирает; правила для агента просят исправить ошибки
своей правки или сообщить о них, остальное — решение пользователя. При `true`
`lipi init` ставит pre-commit `lipi check --staged`, и ошибки
не проходят до коммита. Чужой pre-commit lipi не трогает. Смена ключа
применяется командой `lipi init`; до неё V3 сообщает, что правила
отрисованы с другим значением. Код возврата `lipi check` от `enforce` не
зависит: 0 — чисто, 1 — ошибки, 2 — неверный запуск или настройки.

<a id="levels"></a>Что считать проблемой, тоже решает проект (ADR-012): ключ `codes` в
`lipi.json` задаёт любому коду уровень `"error"`, `"warning"` или `"off"`;
без ключа действуют уровни по умолчанию. C1 и V1 не настраиваются.
Уровень, заданный самим правилом, имеет приоритет над `codes`: повторный
slug заголовка D2 — предупреждение; V3 — ошибка отпечатка или предупреждение
о расхождении `enforce`. Например, `"D7": "off"` разрешает ссылки на заголовки
без явного якоря; цели-разделы у `@trace` и `covers` требуют явного якоря.
Для обычных ссылок в рабочих материалах, правилах исполнителя и корневом
README вне описания отсутствие явного якоря — предупреждение [W9](codes.md#w9).
Рабочие материалы верны на свою дату, а описание всегда должно оставаться
верным: в нём такая ссылка по-прежнему даёт ошибку [D7](codes.md#d7).
Проект может усилить W9 до ошибки; битые ссылки отдельно проверяет W6.
Устаревший указатель рабочих материалов локальный `lipi check` пересобирает
сам; в CI, формате github, с `--staged` или `--diff` сообщает W7 без
пересборки. Пользовательский файл на месте указателя тоже даёт W7.

Быстрый режим проверяет ссылки и якоря, размер и достижимость страниц,
имена и шапки рабочих документов, мастер-план, актуальность указателя и
метки в коде. Ссылками считаются Markdown-ссылки и изображения, а также
HTML `img[src]` и `a[href]` в Markdown-файлах; примеры кода и
HTML-комментарии пропускаются. С ключом `--staged` или `--diff` он
предупреждает, когда код под меткой изменён, а целевой раздел
Markdown-файла нет. Перечень файлов
все команды берут из Git в границах проекта, в том числе вложенного:
отслеживаемые и новые неигнорируемые файлы. Вне Git проверка обходит
файлы по правилам `skip_dirs`.
Игнорируемое не читается и не служит целью. Сначала проверяется исходный
путь в списке Git, затем символическая ссылка и граница разрешённого
каталога. Случайная ссылка наружу не расширяет доступ; явно настроенные
внешние каталоги описания/рабочих материалов и `repos.read` сохраняются.
Настройки, управляемое состояние и список `mv --from` — явные входы команд,
они читаются независимо от отбора содержимого проекта.
Для нумерации `new` учитывает также имена игнорируемых рабочих документов
без чтения текста и перехода по символическим ссылкам.
В Git-проекте `init` и `new` отказывают до записи, если путь создания
рабочего документа проходит через символическую ссылку.

Команды проекта задаются в `checks` и запускаются без оболочки из корня:
ошибка, тайм-аут или отсутствие команды — P1 с именем и хвостом вывода.
Медленным проверкам задают режим `audit`.

Неверные настройки дают C1 и код 2. V1 сверяет версию с
`.agents/lipi/lipi.lock`. У проекта из другой мажорной линии должна быть
подходящая [установка](../../SETUP.md#install) либо правила, применённые
по инструкции из [CHANGELOG](../../CHANGELOG.md). V3 сверяет отпечатки правил и CI.

Аудит проверяет залежавшиеся работы, размер документов, точки входа без
меток, устаревание, отставание статусов от коммитов и размер базовой линии.
Принятое решение со ссылкой на открытое обсуждение даёт A7: проверьте,
можно ли закрыть обсуждение. Необязательный `- Due: ГГГГ-ММ-ДД` у плана
или замечания даёт A8 при просрочке или неверной дате; сегодняшний день
не просрочен, финальные и неизвестные статусы не участвуют.
A7/A8 — предупреждения с уровнем через `codes`; статусы не меняют.

Аудит также справочно считает физические строки с точным признаком
`lipi: ignore-trace` в пределах обхода кода, даже без метки на строке.
В JSON это `summary.ignored_trace_lines`; в текстовом и GitHub-выводе —
отдельная строка, включая ноль. Это не находка: нет кода, предупреждения,
записи базовой линии или влияния на `--strict`. У check без аудита
сводка прежняя. Признак подавляет только метки своей строки: не T2/A4
на её изменение внутри настоящей области, не `covers` и не другие проверки.

История для A4 учитывает переносы кода между файлами и игнорирует пробельные
изменения (`git blame -w -M -C`). Соседние отдельные строки меток образуют
одну группу; её комментарии исключаются из датирования кода. Inline-метка
образует отдельную группу, код рядом с ней учитывается. Аудит и срез
используют одинаковые границы: до следующей группы или конца файла.
Сообщение показывает время кода и раздела в UTC. Для незакоммиченных строк
это единое время проверки, а не время отдельных вызовов Git: совместная
правка кода и целевого раздела считается одновременной и не даёт A4.
Если изменён только код, сравнение с закоммиченным разделом сохраняется.
Аудит и срез используют общий отбор: история файлов и blame без `-C`
отсеивают заведомо актуальные области; остальные проверяются с `-C` по
целому файлу, чтобы сохранить контекст распознавания переноса. Если
безопасность отбора не подтверждена, область требует индивидуальной проверки.
У аудита ограничений нет. Срез ограничивает число файлов индивидуального blame
и явно сообщает объём непроверенного по [договору](slice.md#staleness);
непроверенное подозрение не выдаётся за сигнал A4.

Разобранный A4 можно [подтвердить](review.md#confirm) для одной пары:
две области, автор и объяснение сохраняются с отпечатками в
`.agents/lipi/reviews.json`. Аудит и срез снимают только совпавшую пару;
новая правка любой стороны отменяет отметку. Уровень error также учитывает
просмотр; T2 и covers не меняются. Справочные [счётчики](review.md#summary)
отдельны от находок и базовой линии. Не изменяйте описание только ради даты.

Существующий долг проекта фиксируется базовой линией
`.agents/lipi/baseline.json`: `lipi baseline` записывает текущие ошибки,
`lipi baseline --prune` убирает исправленные и не добавляет новых, проверка
падает только на ошибках сверх линии. В линию не попадают предупреждения и
ошибки настроек C1: с неверными настройками проверке нельзя доверять.

Чекер проверяет форму. Верно ли текст описывает поведение, решает человек.

Для инструментов и CI есть машинный вывод: `lipi check --format json` выдаёт
ошибки, предупреждения и сводку одним объектом JSON, `--format github` —
аннотации GitHub Actions, а с командой `new` JSON отдаёт путь и ID
созданного документа. Ключ `--structure` добавляет к выводу граф связей
проекта: узлы (страницы, явные якоря,
рабочие документы, файлы кода с метками, правила) и рёбра (ссылки описания,
рабочих материалов, правил и README, метки `@trace`, `covers`, ссылки
мастер-плана), с разбивкой `counts` по типам. С `--staged`/`--diff` граф
дополняется цепочкой устаревания `stale`. Набор проверок и коды не
меняются.


## Авторы отметок и сравнение с ревизией <a id="review-authors"></a>

При наличии `reviews.json` аудит добавляет к сводке `reviewed_by`: массив
`{reviewer, count, last_reviewed_at}` по авторам отметок, действительно
снявших A4 в этом запуске. Сумма `count` равна `reviewed_pairs`. Записи,
которые не применились, в эту разбивку не входят; при A4: off массив пуст.
Имена не нормализуются, порядок — по точной строке `reviewer`;
`last_reviewed_at` — максимальное время записей этого автора в UTC.
Пустой реестр даёт `[]`; без файла обычный аудит сохраняет прежние поля.

```bash
lipi audit --reviews-since HEAD
lipi audit --reviews-since <ревизия> --format json
```

Флаг принимает одну Git-ревизию коммита, включая аннотированный тег;
диапазон не поддерживается. Можно передать `--root` проекта внутри Git.
Сравнивается реестр текущего рабочего дерева с `.agents/lipi/reviews.json`
этого проекта на выбранном коммите. Историческое отсутствие файла означает
пустой реестр; отсутствие нынешнего файла — ноль новых записей.

Новой считается текущая запись, чей `id` отсутствовал в старом реестре.
Считается **весь реестр**, включая устаревшие и пока не применённые отметки.
Поэтому число новых может отличаться от числа учтённых A4. Изменение автора,
времени или объяснения при прежнем `id` новую запись не создаёт;
изменение отпечатка или адреса меняет `id` и считается новой записью.
Lipi не определяет автора кода, выпуски проекта или независимость просмотра.

В JSON флаг добавляет `summary.reviews_since` даже без текущего файла:
`revision` — введённая ревизия, `commit` — её полный OID, `count` — число
новых записей, `by_reviewer` — та же разбивка по авторам. Нули — `0` и `[]`.
Оба вида статистики справочные: не меняют findings, коды возврата и
`schema: 1`. Check и slice новых полей не получают; `check --audit`
эквивалентен audit. В обычном check, index, new и baseline флаг недопустим.

Пример фрагмента `summary`: две учтённые пары и одна новая запись.

```json
{
  "reviewed_pairs": 2,
  "reviewed_by": [
    {"reviewer": "Ирина", "count": 2, "last_reviewed_at": "2026-11-18T12:30:00Z"}
  ],
  "reviews_since": {
    "revision": "HEAD~1",
    "commit": "0123456789abcdef0123456789abcdef01234567",
    "count": 1,
    "by_reviewer": [
      {"reviewer": "Ирина", "count": 1, "last_reviewed_at": "2026-11-18T12:30:00Z"}
    ]
  }
}
```

В text и github авторы и сравнение печатаются отдельными справочными
строками с числом и временем. Имена и ревизия заключены в JSON-кавычки;
управляющие символы экранированы, запись занимает одну строку.
Неверная ревизия, отсутствие Git или неподходящая команда — ошибка
аргумента с кодом 2. Повреждённый исторический реестр, каталог или
символическая ссылка вместо него — C1 и код 2, без частичного сравнения.
Исторический файл проходит ту же строгую проверку схемы, что текущий.
Проверки аргументов и снимка выполняются до проектных checks и пересборки
указателя; текущий реестр команда не переписывает.
