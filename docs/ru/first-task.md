# Одна задача с Lipi в существующем проекте

Допустим, экран показывает список записей, а нужно открывать сохранённую
редакцию. Умеет ли сервис уже читать редакцию по ID? Начните с этого вопроса.
Для начала достаточно одного описанного договора, его реализации и теста.

## Найти договор <a id="find"></a>

Начните в каталоге с кодом и документацией проекта. Если Git не отслеживает
выгрузки, добавьте их каталог (например, `exports/`) в `.gitignore`. Если
данные уже в Git или проект ведётся без Git, исключите их каталог из обхода
через [`skip_dirs`](settings.md#skip-dirs) в `lipi.json`. Для пакета
с описанием в `docs/` сначала посмотрите план развёртывания, затем примените
его с теми же параметрами.

```bash
lipi init --docs docs --dry-run
lipi init --docs docs
lipi check
lipi map
```

Если в проекте свой бэклог, в `lipi.json` можно задать `"workflow": null`.
После первого развёртывания `lipi check --no-baseline` покажет также прежние
ошибки, записанные в базовую линию. [Подробности развёртывания](../../SETUP.md#init).

Найдите операцию на карте или возьмите короткую фразу из заголовка страницы
или раздела, например `lipi slice 'чтение сохранённой редакции'`. По точному
адресу `lipi slice 'docs/records.md#read-revision'` сразу откроет срез раздела.
Посмотрите реализацию и связанный с ней клиентский код. Если сервис уже
принимает ID редакции, а экран вызывает операцию получения списка, ясно,
где начинать правку.

## Связать описание с кодом <a id="mark"></a>

В `docs/records.md` дайте проверяемому обещанию свой якорь. Если страница
новая, добавьте ссылку на неё в оглавление документации.

```markdown
## Чтение сохранённой редакции <a id="read-revision"></a>

Чтение редакции по ID возвращает название, сохранённое в этой редакции.
```

Поставьте `# @trace docs/records.md#read-revision` перед функцией,
которая формирует ответ, и перед тестом, который проверяет название.
Используйте синтаксис комментария своего языка. Укажите ту же цель у функции
клиента, которая читает ответ. Если клиент в другом репозитории, к цели
добавляется имя подключения.

## Работать с двумя репозиториями <a id="repos"></a>

Пусть рядом лежат клоны `service/` и `client/`, у каждого свой `lipi.json`.
Добавьте следующие настройки в существующие файлы.

**В `client/lipi.json`** укажите репозиторий, где описан договор.

```json
{"repos": {"service": {"path": "../service", "read": ["docs"]}}}
```

Теперь у читателя в клиенте можно поставить
`@trace service::docs/records.md#read-revision`. Из `client/` выполните
`lipi slice 'service::docs/records.md#read-revision'`.

**В `service/lipi.json`** добавьте обратное подключение, чтобы видеть
потребителя при ревью правок сервиса.

```json
{"repos": {"client": {"path": "../client", "read": ["code", "tests"]}}}
```

Из `service/` выполните `lipi slice 'docs/records.md#read-revision'`.
Найдите читателя с префиксом `client::`. В сводке видно, какие источники
удалось прочитать. Проверка устаревания охватывает локальные связи. Когда
ответ меняется, сверьте с ним читателя у соседа. [Настройки подключений](settings.md#repos).

## Проверить изменение <a id="review"></a>

Допустим, у функции, формирующей ответ, есть также метка на общий раздел
`docs/records.md#display` о показе записи. На него ссылаются и экран
клиента, и предпросмотр экспорта. После правки отслеживаемого кода этой
функции выполните `lipi slice --diff HEAD` в `service/`. По подписям
видно, почему в срез попало каждое место в клиенте.

| Место в клиенте | Подпись | Что посмотреть |
| --- | --- | --- |
| Читатель редакции | `через #read-revision` | Может ли он прочитать изменившийся ответ? |
| Экран записи | `через #display` | Что видит пользователь? |
| Предпросмотр экспорта | `через #display` | Использует ли этот отдельный экран изменившееся поле? |

Общая метка объясняет связь. Откройте код, чтобы установить, кто вызывает
операцию. Читатель может принять новое необязательное поле, а экран по-прежнему
будет показывать только прежние поля. [Срез по диффу](slice-diff.md#response).

В тесте выбора редакции сделайте текущей редакцию B, задайте редакциям A и B
разные названия и запросите A. Проверьте, что ответ содержит название A.
Проверка ID, скопированного из запроса, прошла бы и с содержимым B.
Запустите тест, если ваш вывод зависит от этого поведения.

Если позже понадобится найти Markdown-страницы за пределами каталога
описания соседа, добавьте [`page_dirs`](settings.md#repos) в это подключение
и воспользуйтесь [поиском по заголовку](slice-output.md#repo-search).
