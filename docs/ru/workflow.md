# Указатель рабочих материалов

Статус и итог работы хранятся в шапке её документа. `lipi index` собирает
из этих шапок короткий вход и отдельные списки. Имена документов, годовые
каталоги и поля шапки описаны в [правилах](rules.md#workflow).

## 1. Комплект файлов <a id="files"></a>

Пути ниже отсчитываются от каталога `workflow` из `lipi.json`:

| Файл | Содержимое |
| --- | --- |
| `INDEX.md` | работы «in progress», планы «pending acceptance», счётчики и ссылки на списки |
| `index/plans.md` | планы: new, in progress, pending acceptance, deferred |
| `index/issues.md` | замечания: open, in progress |
| `index/discussions.md` | обсуждения: open |
| `index/decisions.md` | решения: proposed, accepted |
| `index/audits.md` | все аудиты |
| `index/done/ГГГГ.md` | работы, закрытые в этом году: финальные статусы из таблицы ниже |

Активная работа может одновременно находиться в коротком входе и в своём
списке; общий счётчик считает каждый документ один раз. Принятое решение
остаётся действующим и входит в `decisions.md`. Замечания из
`.agents/lipi-feedback/` и архивные материалы в указатель не входят.

Заголовки и служебные строки указателя всегда на английском. Названия работ и итоги берутся из исходных документов.

Фиксированные файлы создаются даже при пустом списке. Исключение —
игнорируемые Git пути: они не читаются, не создаются и не входят в ссылки
указателя. Пустая ранее созданная
страница года сохраняется с сообщением `No closed work items.`, чтобы
ссылка на год продолжала работать.

## 2. Год журнала и результат <a id="closure"></a>

| Тип | Финальные статусы |
| --- | --- |
| План | completed, canceled |
| Замечание | closed |
| Обсуждение | closed |
| Решение | superseded, rejected |

Год страницы `done/ГГГГ.md` берётся только из строки
`- Closed: ГГГГ-ММ-ДД`. Неизвестный или чужой для типа статус
финальным не считается. У аудита нет финального статуса и даты закрытия.

Отсутствующая обязательная дата даёт [W4](codes.md#w4). Некорректная
календарная дата, дата раньше создания или позже календарной даты UTC
плюс один день даёт [W3](codes.md#w3). Допуск учитывает разницу часовых
поясов; граница одинакова для проверки, указателя и переноса материалов.
Пока у финального документа нет корректной даты
закрытия, весь комплект остаётся без изменений: частичный журнал не пишется.

Генератор не читает историю Git для вычисления дат и не дописывает шапки.
Дата закрытия в строке журнала сохраняется после поздней правки,
переименования или слияния, одинаково с Git и без него. Год создания
определяет каталог документа, а год закрытия — только страницу журнала.

Повторно открытая работа возвращается в живой список. При следующем
закрытии исполнитель явно указывает новую дату; переход между двумя
финальными статусами сам по себе дату не меняет.

Правка заголовка, итога или адреса обновляет строку на той же странице
года. Относительные ссылки из итога пересчитываются от каждой страницы
указателя и сохраняют цель и якорь. Внешние адреса, абсолютные ссылки и
примеры в коде остаются как в исходном документе; его текст не меняется.

## 3. Владение файлами <a id="ownership"></a>

Производный файл начинается с явного маркера:

```html
<!-- lipi:generated:workflow-index -->
```

Маркер действует только на точных путях из таблицы комплекта. Остальные
файлы в `index/` не становятся указателями и не удаляются. Новый целевой
путь, занятый пользовательским файлом, останавливает пересборку до записи.
Символьные ссылки на участвующих путях указателя также дают отказ.

Ручные правки помеченного указателя заменяются пересборкой. Если байты
не изменились, файл повторно не записывается. Сам указатель коммитится
вместе с рабочими документами; генератор не добавляет его в индекс Git.

## 4. Пересборка и проверка <a id="refresh"></a>

После изменения шапки рабочего документа:

```bash
lipi index
```

Команда собирает весь комплект, проверяет пути и владение файлами, затем
записывает изменения. Ошибка записи или прерывание откатывает записанные
файлы и созданные каталоги.

Локальный `lipi check` пересобирает устаревшие файлы автоматически.
В CI, с `--staged`, `--diff` или `--format github` проверка не пишет
указатели: [W7](codes.md#w7) сообщает каждый устаревший файл отдельно.
Явный `lipi index` пересобирает комплект и в этих окружениях.

После успешной пересборки ссылки и граф проверяются по новым страницам.
Создание и сбор рабочих документов используют тот же комплект, поэтому
отдельно поддерживать списки или журнал не нужно.

## 5. Разложить документы по годам <a id="upgrade"></a>

Если документы оформлены по [правилам lipi](rules.md#workflow), но лежат
прямо в каталогах типов, `lipi init` разложит их по годам создания и
применит правила в рамках одной операции. Из корня Git-репозитория
просмотрите план и выполните его:

```bash
lipi init --dry-run
lipi init
lipi check
```

В плане видны прежние и новые пути, изменения правил, состояния и
указателей. PLN, ISS, DSC и AUD переезжают в каталог года из поля `Created`;
папка документа переносится вместе с приложениями. Номера сохраняются,
ADR и `.agents/lipi-feedback/` остаются на месте, архив не переносится.
Оформленные документы можно перенести при первом подключении lipi и при
повторном применении правил. Материалы в другом формате импортирует
команда [`lipi migrate`](commands.md#migrate).

Если хотя бы один документ переносится по годам, для финальных документов без `Closed` вычисляется дата последнего закрытия.
При уже годовой раскладке пропущенный `Closed` нужно заполнить в шапке.
В старых коммитах распознаётся и русское поле «Статус». Если у файла нет истории Git, берётся `Updated`.
Если история есть, но HEAD не подтверждает финальный статус, команда сообщает об ошибке.
Каждое добавляемое значение и его источник показаны в плане. Для записанной
и вычисленной даты действует общая [граница по UTC](#closure). Корректная
записанная дата сохраняется; повторный init её не пересчитывает.
Нечитаемая или неоднозначная история не заменяется догадкой.

Перед записью проверяется весь план. Отказ с путём и причиной получают:

- внешний каталог рабочих материалов, плоские документы без
  Git или перевод из каталога, не являющегося корнем репозитория;
- неверные даты шапки, повторный номер, неоднозначное размещение или год,
  расходящийся с Датой создания; для последнего сначала нужен `lipi mv`;
- незакоммиченные изменения затрагиваемых файлов, конфликт Git, занятый
  путь назначения, чужой файл на пути нового указателя или символьная ссылка;
- некорректное состояние baseline/reviews либо изменение просмотренной
  области, для которого нельзя сохранить подтверждение адресным переносом.

Отказ происходит до обновления lock. При ошибке записи или прерывании
общий план откатывает перемещения, файлы, права, каталоги и индекс Git.
Правила, hook, шапки, базовая линия, действующие просмотры и весь комплект
указателей применяются вместе. Адресные ключи baseline и подтверждённые
переносимые пары A4 переводятся без принятия нового долга и без повторного
подтверждения смысла; код, число повторов и неадресный смысл находок сохраняются.
Посторонние изменения и уже подготовленные файлы в индексе сохраняются.
Перемещения видны в Git, остальные правки нужно просмотреть и добавить
явно. Новая правка извне во время отката сохраняется с сообщением о
неполном откате.

Развернуть каркас с годовой структурой можно без Git. Уже размещённые по
годам документы остаются на месте. Если их шапки требуют исправлений,
проверьте находки `lipi check`.

При первом создании базовой линии dry-run показывает её файл, а команды
проекта для определения долга выполняются только при реальном применении.
