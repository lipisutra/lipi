# Коды проверок

Чекер проверяет каталог описания, рабочие материалы, `AGENTS.md`, правила
проекта в `.agents/` и ссылки корневого `README.md`; правила lipi в
`.agents/lipi/` и шаблон CI сверяются с отпечатками в lock-файле.

В Git-репозитории, включая вложенный проект, перечень файлов для проверок
берётся из Git в границах проекта: отслеживаемые и новые неигнорируемые.
Новые файлы участвуют до `git add`; `.gitignore` исключает неотслеживаемые
файлы. Явные внешние каталоги описания и рабочих материалов используют
свой перечень Git; вне Git чекер обходит каталоги;
`skip_dirs` действует в обоих случаях: [имя или путь от корня](settings.md#skip-dirs).

Быстрые проверки обязаны укладываться в бюджет скорости: на синтетическом
проекте в 300 страниц и 5000 файлов кода — не дольше 2 секунд; это проверяет
`tests/test_speed.py` в CI.

Код проверки — постоянный идентификатор: коды не переиспользуются. Новая
проверка получает новый код, а снятая не отдаёт свой код другой. На коды
ориентируются CI, базовая линия и человек в выводе, поэтому смысл кода между
версиями не меняется.

У каждой строки таблицы есть явный якорь (`<a id="d1"></a>`, `<a id="w8"></a>`
и так далее): на них ссылаются метки `@trace` самого чекера в
модулях `src/lipi/checker/` — правка проверки видна в её описании.

Ключ `checks` (имя, команда, режим, предел времени) описывает
[settings.md](settings.md).

T1 и D6: файл проходит [отбор проекта](checking.md), явный якорь в нём единственный; номер найден
вне архива. `AGENTS.md` и свои файлы `.agents/` разрешены; исключены
`skip_dirs`, `.agents/lipi/` и `history/` корня, workflow и decisions.
Отсутствующая, исключённая или неоднозначная цель — T1 у метки, D6 у
`covers`. При `"workflow": null` доступны лишь ADR из явного `decisions`.

ADR ищется в `decisions`, без ключа — в `<workflow>/adr/`. Имена `001-…`,
`0001-…` и `adr-001-…` обозначают `ADR-001`; номера нормализуются одинаково
для меток, `covers`, среза и поиска дублей. Два разных файла с одним
номером дают неоднозначность, а не выбор первого. Решения не входят в
D3/D4 и языковые пары описания; шапки, ссылки и якоря проверяются.

T3 проверяет статус разрешённой цели по номеру одинаково у `@trace` и
`covers`. Например: «ISS-007 closed — проверьте, нужна ли связь; если это
временный обход, его можно убрать».

| Тип цели | Статусы с T3 | Действие |
| --- | --- | --- |
| Решение | superseded, rejected | сверить код с новым решением или пересмотреть опору на отклонённое |
| Замечание | closed | проверить, нужна ли связь; если это временный обход, его можно убрать |
| План | completed, canceled | проверить актуальность связи с завершённой или отменённой работой |
| Обсуждение | closed | сверить код с итогом обсуждения |

Остальные допустимые статусы, аудиты и цели-разделы Markdown не дают T3.
Неверный статус относится к W3, дополнительного T3 нет. Для заменённого
решения сообщение называет преемником только первый рабочий документ из
ссылок в поле «Result» шапки; без такой ссылки сообщение остаётся без
преемника. Например: «superseded ADR-010 — сверьте код с новым решением».

Обычная ссылка из описания или правил исполнителя на заменённое либо
отклонённое решение также даёт T3: «ссылка ведёт на заменённое решение
ADR-NNN — проверьте актуальность текста». Исторические ссылки рабочих
материалов не сигналят. Ссылка на раздел решения тоже проверяет его статус.

T3 по умолчанию предупреждает и не останавливает проверку. Если проект
задаёт `"codes": {"T3": "error"}`, базовая линия различает основания по
`subject`: номеру и статусу, например `ISS-007 closed`. Переход решения
из «rejected» в «superseded» даёт новый сигнал, который прежняя запись
линии не поглощает. При уровне `warning` T3 в базовую линию не записывается;
`off` выключает сигнал для меток, `covers` и обычных ссылок.

Языковые редакции проверяются по ключу `languages`: D1–D5 идут в каждой
редакции, D4 — от `README.md` своей редакции, L1 и L2 сверяют пары страниц по
относительному пути, L3 — ссылки между редакциями. Пути `@trace` и `covers`
разрешаются от корня проекта, включая каталог нужной редакции.

V2 и V3 работают при наличии корректного `.agents/lipi/lipi.lock`, даже с
пустым списком отпечатков; без lock обе молчат. Пустой список означает
неполное развёртывание: V3 предлагает `lipi init`. Проверяет установленная
команда `lipi`; сам lipi проходит те же проверки по своему lock-файлу.
Правила агента отрисовываются по `enforce` из `lipi.json`, и
lock-файл хранит значение, с которым их отрисовал `lipi init`: расхождение
с настройками — V3 с подсказкой запустить `lipi init`.

Замечания к lipi из `.agents/lipi-feedback/` проверяются как замечания (W1,
W3, W4, W6, W8, W9), их номера общие с `workflow/issue/` (W2), а в указатель они
не входят.
