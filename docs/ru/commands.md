# Команды lipi

Запускайте команды из корня проекта; `mv` работает и из подкаталога.
Чекер входит в установленный пакет. Установка — в [SETUP.md](../../SETUP.md).

## Работать с проектом

| Команда | Назначение |
| --- | --- |
| <a id="help"></a>`lipi help` | Справка; то же без аргументов и с `-h`, `--help`, `?`, `/?`. `lipi help slice`, `lipi help map`, `lipi help mv` и `lipi help review` дают справку выбранной команды. |
| <a id="lang"></a>`lipi lang [язык]` | Показать или выбрать [язык интерфейса](settings.md#interface-language). Для русских заготовок выполните `lipi lang ru` перед первым `lipi init`. |
| <a id="guide"></a>`lipi guide` | Печатает [SETUP](../../SETUP.md) из репозитория или установленного пакета; если страницы нет — её адрес на теге своей версии и код 1. |
| <a id="check"></a>`lipi check` | [Быстрые проверки](checking.md); `--staged` добавляет детектор расхождения по индексу Git, `--diff A...B` — по диапазону. `--strict` считает предупреждения ошибками, `--no-baseline` показывает все ошибки. |
| <a id="audit"></a>`lipi audit` | Check и расширенный [аудит](checking.md); справочно — ignore-trace и авторы отметок. `--reviews-since <ревизия>` показывает [новые отметки](checking.md#review-authors). |
| <a id="index"></a>`lipi index` | Пересобирает полный [комплект указателей](workflow.md): короткий INDEX, живые списки и журнал по году поля `Closed`. |
| <a id="baseline"></a>`lipi baseline [--prune]` | Записывает ошибки в `.agents/lipi/baseline.json`, после чего проверка падает только на новых. Предупреждения не входят; `--prune` убирает исправленное, не добавляя нового. Линия коммитится вместе с проектом. |
| <a id="new"></a>`lipi new <тип> "Название" [вид] [lipi]` | Создаёт документ в годе создания со сквозным номером; ADR/feedback плоские. Типы: `pln`, `iss`, `dsc`, `adr`, `aud`. У замечания `Kind` — bug, friction, request или question; адресат `lipi` позволяет создать его и без рабочих материалов в `.agents/lipi-feedback/`. |
| <a id="selftest"></a>`lipi selftest` | Запускает локальный набор unittest самого lipi из его репозитория. Если каталога тестов нет — сообщение и код 2. |
| <a id="version"></a>`lipi version [--path]` | Версия пакета; `--path` добавляет путь к его чекеру. `lipi --version` — тот же обработчик. |

Например:

```bash
lipi map                       # карта разметки: цели, слои кода, тесты
lipi slice docs/api.md#requests  # срез по понятию перед задачей
lipi check --format json --structure  # находки и граф структуры
lipi new pln "Название плана"
lipi new iss "Что сломалось" bug
lipi new iss "Что мешает" friction lipi
```

## Просмотр A4 <a id="review"></a>

`lipi review <путь#якорь> --at <файл[:строка]> --full` показывает пару A4 и token.
После чтения обеих сторон подтвердите его с автором и объяснением.
`lipi review --prune` показывает план уборки. Подтверждение, файл, JSON и
перенос — в [договоре](review.md); `lipi help review` — справка.

## Карта проекта <a id="map"></a>

`lipi map` показывает таблицу прямых меток по целям, слоям кода и тестам. Нули означают
отсутствие связей, а не реализации. `lipi map --format json` отдаёт те же строки и числа;
`lipi help map` — справку с адресом карты выбранной редакции. Только чтение, без истории и проверок; [договор карты](map.md).

## Срез перед задачей <a id="slice"></a>

`lipi slice <цель>` собирает правила, сигналы, места в коде и тесты по разделу, странице,
файлу кода или номеру работы. Только читает; не запускает проверки, не меняет линию и указатель.

```bash
lipi slice docs/api.md#requests
lipi slice src/api.py --format json
lipi slice ISS-007
lipi slice --diff HEAD   # либо --staged: связи изменений для проверки
```

Формы целей, блоки, предел, флаги и JSON — в [договоре среза](slice.md),
[дифф](slice-diff.md), [примеры](slice-examples.md). Коды возврата: 0 — ответ получен,
включая пустой; 1 — цель не найдена или неоднозначна; 2 — неверный запуск или настройки.
Сигналы в полученном ответе код возврата не меняют.

## Перенести страницу или каталог <a id="mv"></a>

`lipi mv <старый путь> <новый путь>` переносит страницу или каталог;
`lipi mv --from <файл>` — список переносов. Без `--apply` печатается общий
план с точными заменами; `lipi help mv` показывает справку.
Позиционные пути — от текущего каталога, пути внутри списка — от корня Git-репозитория.
Каталог и список требуют чистых затрагиваемых файлов в дереве и индексе;
одиночная страница сохраняет локальные правки. Состав операции, ссылки,
отказы, откат и коды возврата — в [описании переноса](move.md).

## Вывод <a id="output"></a>

Находки `check` и `audit` печатаются в одном из трёх форматов — ключ `--format`:

| Формат | Для чего |
| --- | --- |
| `text` (по умолчанию) | человек: по строке на находку, `путь: [ошибка D1] …` или `путь: [предупреждение V1] …` |
| `json` | инструменты и CI: один объект JSON по схеме ниже |
| `github` | аннотации GitHub Actions: `::error` для ошибок и `::warning` для предупреждений |

```bash
lipi check --format json
lipi check --format json --structure   # + граф структуры: узлы и рёбра
lipi check --format github             # в CI на GitHub Actions
lipi new pln "Название" --format json  # путь и ID документа в JSON
```

Сообщения lipi в JSON всегда английские. Пример для схемы 1:

```json
{
  "schema": 1,
  "version": "1.0.0",
  "errors": [
    {"code": "D1", "file": "docs/guide.md", "line": 12,
     "subject": "nope.md", "message": "link points to a file that does not exist: nope.md"}
  ],
  "warnings": [],
  "baseline": {"known": 0, "fixed": 0},
  "summary": {"pages": 4, "docs": 12, "tags": 3, "errors": 1, "warnings": 0}
}
```

- `errors` и `warnings` — находки; у каждой `code` — код проверки, `file` —
  путь от корня проекта, `line` — номер строки (`0` — нет), `subject` —
  устойчивая суть находки без чисел и формулировки (цель ссылки, якорь, имя
  поля шапки, раздел): по `code`, `file` и `subject` ошибки сопоставляются с
  базовой линией, поэтому сдвиг строк её не ломает;
- `baseline` — сколько ошибок покрыто базовой линией (`known`) и сколько из
  неё исправлено (`fixed`); ошибки, покрытые линией, в `errors` не попадают;
- `summary` — число страниц описания, рабочих документов и меток, ошибок и
  предупреждений;
- `structure` — граф структуры, только с `--structure`: `nodes` (страницы
  описания, разделы других Markdown-файлов, рабочие документы, код с метками),
  `edges` (ссылки, метки на разделы и номера работ,
  `covers`, ссылки мастер-плана), `counts`; при `--staged` или `--diff` ещё
  `stale` — цепочка устаревания. Граф — производное представление уже
  вычисленных проверками связей, источник истины не он; его форма закреплена
  эталонами `tests/fixtures/*.structure.json`;
- `new … --format json` печатает свой объект: `path` — путь документа от
  корня проекта, `id` — его номер, `index_updated` — обновлён ли указатель.

Пример `--format github` при `lipi lang ru`:

```text
::error file=docs/guide.md,line=12,title=D1::ссылка ведёт в несуществующий файл: nope.md
::warning file=.agents/lipi/lipi.lock,title=V1::обновите lipi: pipx upgrade lipi
```

`file` опускается, если у находки нет файла, `line` — если номер строки
неизвестен (`0`). Спецсимволы в сообщении и значениях параметров
экранируются по правилам GitHub Actions. В `github` нет общей сводки и базовой линии, но есть справочные строки
об отметках и ignore-trace. Машинная форма — только JSON.

Коды возврата `check` и `audit` одинаковы для всех форматов:

| Код | Когда |
| --- | --- |
| 0 | новых ошибок нет; с `--strict` нет и предупреждений |
| 1 | есть новые ошибки; с `--strict` — и предупреждения |
| 2 | неверный запуск (неизвестный ключ, `--format` не из списка) или C1: настройкам нельзя доверять, проверки не запускались |

## CI в проекте <a id="ci"></a>

`lipi ci github` кладёт в проект задание CI — `.github/workflows/lipi.yml`
(с каркасом его создаёт `lipi init --ci github`): при push и pull request
задание ставит lipi той же первой цифры (`pipx install
git+https://github.com/lipisutra/lipi@v<цифра>`) и проверяет установленной
командой с аннотациями GitHub Actions. Шаблон всегда английский. V3 сверяет
файл с lock, повторный `init` применяет шаблон заново.

Для другой системы CI достаточно одной команды запуска — например, на pull
request с полной историей:

```bash
lipi check --diff origin/main...HEAD --format github
```

В CI нужна установленная команда `lipi` (ADR-010): проект её не содержит, а
ставит её шаг установки пакета.

## Диагностика <a id="doctor"></a>

Если проверка ведёт себя странно или непонятно, с чего начать, —

```bash
lipi doctor
```

Команда печатает по строке на пункт: версия Python; версия установленного
lipi; есть ли `lipi.json` и `.agents/lipi/lipi.lock`, версия проекта из
lock-файла и её совместимость с установленным lipi по первой цифре;
pre-commit — по ключу `enforce` (при `true` хук lipi должен стоять, при
`false` его быть не должно); раскладку и даты шапок рабочих материалов;
актуален ли комплект указателей; есть ли базовая линия и сколько в ней записей и ошибок. Строка кончается на «ок»
или на «[проблема]» с подсказкой, что запустить: `lipi init`,
`pipx upgrade lipi`, `lipi index`.

Код возврата 0 — проблем нет, 1 — есть хоть одна. Команда только читает:
ничего не создаёт и не правит, поэтому работает и в каталоге без
развёрнутого проекта — тогда она печатает, что запустить (`lipi init`).

## Применить правила установленного lipi <a id="update"></a>

Программу обновляет установщик: `pipx upgrade lipi`. Затем раздел
«Проекту при обновлении» в [CHANGELOG](../../CHANGELOG.md) говорит, нужен ли
`lipi init`. Команда применяет файлы из установленного пакета, без сети.

```bash
lipi init [папка]          # развернуть или применить правила установленного lipi
lipi init --dry-run        # только показать, что изменится
lipi init --enforce        # строгий режим нового проекта
```

Признак повторного применения — наличие `.agents/lipi/lipi.lock`:

| Состояние | Действие |
| --- | --- |
| Нет lock и `lipi.json` | создать настройки, недостающие заготовки и файлы lipi; существующие файлы сохранить |
| Нет lock, есть `lipi.json` | сохранить настройки и заготовки, создать недостающие файлы lipi |
| Есть lock и `lipi.json` | заменить или восстановить управляемые файлы lipi; заготовки и базовую линию сохранить, отсутствующие не создавать |
| Повреждён lock/настройки или есть lock без `lipi.json` | ошибка с кодом 2 до записи |

При первом развёртывании отсутствующая базовая линия создаётся, существующая
сохраняется. Ссылку на `.agents/lipi/README.md` в существующий `AGENTS.md`
добавляет проект; новый файл из заготовки уже содержит её.

`--type`, `--docs`, `--workflow`, `--enforce` задают настройки нового проекта.
При существующем `lipi.json` явно заданный аргумент должен совпадать с ним;
иначе ошибка с подсказкой изменить ключ в файле. `--ci github` подключает
шаблон CI; уже подключённый шаблон применяется и без этого флага.

Init пересобирает указатели как [производные файлы](workflow.md#ownership).

`lipi init` берёт правила и CI из английских шаблонов пакета, в том числе
при повторном запуске на той же версии. Если файл расходится с отпечатком
в lock, `--dry-run` сообщает «ваши правки в X будут заменены», а применение
плана — «ваши правки в X заменены». Хук с меткой lipi приводится к `enforce`,
чужой сохраняется. Lock получает версию, отпечатки шаблонов и значение `enforce`.
При отсутствии изменений файлы не перезаписываются. Вывод называет версию
установленного пакета; `--dry-run` показывает план без записи.

Для проекта, развёрнутого более новой мажорной версией, сначала обновите
программу. Init поддерживает [перенос оформленных документов по
годам](workflow.md#upgrade). Для импорта материалов в другом формате
используйте [`lipi migrate`](#migrate).

## Трение с правилами <a id="friction"></a>

Если в проекте правило мешает, чекер ошибается или чего-то не хватает,
исполнитель заводит там замечание с полем `Recipient: lipi`:

```bash
lipi new iss "Что мешает" friction lipi
```

При `"workflow": null` замечание пишется в `.agents/lipi-feedback/`:
каталог создаётся этой командой и коммитится вместе с проектом.

Забрать замечания в lipi — из клона lipi, копии пишутся в него; так же
работает `lipi collect` при установке `--editable`:

```bash
python3 src/lipi/collect.py /путь/к/проекту [/путь/к/другому ...]
```

Копии попадают в `workflow/issue/ГГГГ/` по сегодняшней дате создания. Пометка —
`- Source: external <6 знаков хеша> ISS-NNN`. Хеш — первые шесть шестнадцатеричных знаков SHA-256 от имени
каталога проекта в UTF-8. Повторный сбор с тем же именем каталога и номером
замечания не создаёт дубль. Перед сбором обезличьте заголовок и текст
замечания: они копируются без изменений.

## Похожие замечания <a id="similar"></a>

`lipi new iss "Название"` после создания показывает до пяти похожих
замечаний со статусом «open» или «in progress» из общей очереди рабочих
материалов и `.agents/lipi-feedback/`. Это подсказка проверить существующие
работы; она не объявляет дубль и не требует подтверждения. Нет совпадений —
нет подсказки. Новый файл, архив, `skip_dirs` и игнорируемые git файлы исключены.

Сравниваются множества слов Unicode без учёта регистра, длиной от трёх
символов; пунктуация и подчёркивание разделяют слова. Морфологии нет.
Нужны хотя бы два общих слова и доля общих слов в объединении не меньше
0,5; одинаковые непустые множества проходят и с одним словом.
Порядок: доля по убыванию, затем ID и путь. JSON у `new iss` получает
`similar`: массив объектов `id`, `path`, `title`, `status`; без совпадений —
`[]`. У остальных типов документа этого поля нет.

## Создать решение <a id="new-decision"></a>

`lipi new adr "Название"` создаёт решение в каталоге `decisions` из
`lipi.json`, без ключа — в `<workflow>/adr/`. Явный `decisions` работает
и при `"workflow": null`; недостающий каталог создаётся командой.
Если есть имена без префикса, например `0001-example.md`, следующее —
`0002-….md`. При разных ширинах берётся максимальная среди таких имён;
без них используется `adr-NNN-….md`. Номер учитывает также архивные имена;
при пустом каталоге из них берётся и соглашение об именах. Подробнее —
в [правилах рабочих материалов](rules.md#workflow). В JSON — канонический
`ADR-NNN`. Шапку и текст заполняет проект.

## Перенести рабочие материалы <a id="migrate"></a>

Если планы и замечания проекта лежат по каталогам статусов (`current/`,
`completed/`, `backlog/`), а журнал и мастер-план ведутся руками, их можно
перевести на правила одной командой:

```bash
lipi migrate            # план переноса: что и куда переедет; ничего не меняется
lipi migrate --apply    # выполнить
```

Нужен Git с чистым деревом; перенос выполняется через `git mv`.
Команда сохраняет номера, принимает прежние русские шапки и записывает английские поля, статусы, виды и служебные заголовки. Текст работы сохраняется.
Год: `Created` → первый коммит → сегодня; ADR плоские. `Closed`: из Git, иначе `Updated`.
План называет основания дат. Прежний журнал,
мастер-план и отчёты уходят в `history/`; таблица переноса — в `history/MIGRATION.md`.
Затем пересобирается указатель. Каталог берётся из `workflow` в `lipi.json`;
явно переданный другой каталог записывается в настройки. План заканчивается точной
командой, например `lipi migrate workflow --apply`. Она работает и при `"workflow": null`:
каталог указывают и для просмотра плана, и при применении. [Порядок действий](../../SETUP.md#existing-workflow).

Отдельные документы переопределяются файлом `migrate.json` рядом с рабочими материалами:

```json
{"files": {"current/roadmap.md": {"type": "pln", "status": "in progress", "number": 7}}}
```

В ключе `files` — пути относительно каталога материалов; `type` — `pln`, `aud`, `dsc`, `adr` или `iss`;
`status` — значение из списка своего типа (таблица в
[правилах рабочих материалов](rules.md#workflow));
`number` — целое больше нуля. Неизвестный ключ, тип или статус — отказ с кодом 2.
`migrate.json` нужен только для разового переноса: после него файл можно удалить.
