# Форма и предел ответа среза

Поля JSON, история и отбор содержимого. Цели и состав блоков — в [договоре среза](slice.md).

## Проверка устаревания <a id="staleness"></a>

Дата описания берётся по тем же строкам, что [выдержка](#budget): область
заголовка, абзац, пункт или строка таблицы вместе с шапкой. Строки между
шапкой и выбранной строкой таблицы в область не входят. T2 и A4 используют
то же правило: правка соседнего текста не скрывает устаревание.

Общий отбор по Git-истории охватывает все места: файл, не менявшийся после
своего раздела, даёт точный ответ об отсутствии устаревания. Такие места
входят в `checked` и не расходуют пределы индивидуальной проверки.
Переименование считается изменением; грязные файлы и случаи, в которых
история не позволяет безопасно сделать вывод, идут на индивидуальную проверку.

Для оставшихся файлов действуют две константы: не более 64 файлов
дешёвого blame без `-C` и не более 16 из них с точным поиском переносов.
Порядок детерминирован: точки входа, остальные места кода, тесты; внутри
каждой группы — путь и строка, независимо от порядка слоёв.
Файл учитывается один раз, проверяются все его области. Это не настройки
и не таймер; `lipi audit` проверяет всё без этих пределов.

Подозрение без точной проверки не становится сигналом. При неполной
проверке рядом со сводкой всегда написано: «устаревание проверено для
N из M мест; полная проверка — lipi audit». В JSON это `notes` с кодом
`staleness-partial` и `checks.staleness`:

```json
{"state": "partial", "checked": 60, "total": 1000}
```

В `total` считаются уникальные места (блоки меток) среза с метками на его
разделы, включая тесты. Срез файла включает места в самом файле.
В диффе учитываются [места](slice-diff.md#response) с текущими разрешёнными связями.
Место с несколькими метками считается проверенным, когда проверены все
его связи с разделами среза. Недоступная история тоже оставляет место
непроверенным. При выключенном A4 `total` и `checked` равны 0.
`state` — `full`, если проверено всё, `partial`, если часть осталась,
`no-git`, если Git недоступен (тогда `checked` равен 0). Проект в подкаталоге
репозитория использует его историю: A4 и отметки работают как в корне.
Отсутствие списка файлов для обхода само по себе не означает `no-git`.
При `full` и ненулевом `total` рядом со сводкой тоже показано «устаревание
проверено для N из M мест» (`notes[].code` — `staleness-full`).
`--only`, `--layer`, `--role`, `--full` и предел вывода не меняют охват истории.

При подключениях `checked` и `total` описывают локальную A4. В примечании
`cross-repo-staleness` каждое место с разрешённой межрепозиторной связью
учитывается один раз, включая тестовые места. Счёт охватывает прочитанные
источники. Когда число определить нельзя, примечание сообщает о границе
проверки без числа. Место с обоими видами связей учитывается и в локальном охвате.

## Предел <a id="budget"></a>

- Предел — на весь ответ: `slice_budget` строк содержимого, целое число
  от 1, по умолчанию 60; другое значение — C1. Строка цели, сводка,
  заголовки блоков, `notes` и строки о скрытом в него не входят.
- Элемент, включая основание с несколькими `via`, — одна строка; выдержка — по своим строкам, не больше
  `max(1, slice_budget // 3)`.
- **Граница выдержки.** Якорь в заголовке — от заголовка до следующего
  заголовка того же или более высокого уровня. Якорь в строке таблицы —
  строка заголовка таблицы и эта строка. Якорь в абзаце или пункте списка —
  этот абзац или пункт. У решения по номеру — его раздел «Decision».
- **Сокращение выдержки.** Влезает в свою долю — целиком; иначе первый
  абзац, заголовки подразделов и строки со ссылками в исходном порядке,
  с пометкой «обрезано». Если текст начинается со списка, берётся первый
  пункт с продолжением, а не весь список. Заголовки и ссылки внутри
  ограждённых блоков кода не считаются структурой текста. Не влезает и так
  — обрезается по строкам до доли. `--full` отдаёт выдержку целиком и не
  расходует предел остальных блоков.
- **Распределение** — в строках, по порядку ответа:
  1. сигналы `error` и `warning` — до половины предела
     (`slice_budget // 2`, не меньше 1); остальные из них участвуют в
     шаге 3 первыми;
  2. каждому непустому блоку, кроме сигналов, — до 3 строк, выдержке — до
     3 строк, сигналам `info` внутри блока сигналов — до 3 строк; `error` и
     `warning` обслуживаются шагами 1 и 3;
  3. остаток — снова по порядку ответа, выдержке до её доли.

  Если остатка не хватает на шаг 2 всем, он раздаётся по порядку ответа:
  гарантия «по три» действует, только когда место есть. Так большой блок
  мест в коде или открытых работ не вытесняет тесты целиком.
- Скрытое честно названо в конце блока: число и флаги, которые его покажут.
- Сводка считает все подтверждённые сигналы; скрытые сигналы названы, как и в других
  блоках: «показано 30 из 42 сигналов; ещё — `--only signals`».
- `--only` оставляет названные блоки и всегда сигналы; предел действует.
  С `--only signals` предел целиком у сигналов.
  `--layer` сужает `entry`, `code` и `tests` до слоёв; повторяется.
- JSON отбирает ровно те же элементы и строки выдержки, что текст.

Отбор при правке Markdown с якорями описан в разделе
[«Выдержки разделов»](slice-diff.md#excerpts).

## Пустые срезы <a id="empty"></a>

| Случай | Текст | `notes[].code` |
| --- | --- | --- |
| у раздела или страницы нет меток | меток нет — ищите по коду | `no-marks` |
| решение без меток | кода по этому решению нет | `no-code` |
| работа без ссылок и меток | работа ни на что не ссылается и меток на неё нет | `work-empty` |
| файл кода без меток | в файле нет меток — понятия неизвестны, ищите по коду | `file-no-marks` |
| в части слоёв меток нет | в слоях X, Y меток нет | `layers-no-marks` |
| нет git | устаревание не проверено (нет git) | `no-git` |

## JSON <a id="json"></a>

Верхний уровень: `schema` (сейчас 1), `target`, `summary`, `blocks` в
порядке вывода, `incomplete` (что-то скрыто, выдержка обрезана или история
проверена частично), `notes`,
`checks`. У блока — `kind`, `items`, `omitted` (сколько скрыто), `hint`
(флаги, которые покажут скрытое). Поля элементов:

| Элемент | Поля |
| --- | --- |
| место в коде | `path`, `line`, `symbol`, `layer`, `via` (метка, через которую вошло) |
| тест | `path`, `line`, `symbol`, `layer` |
| документ | `target` (`путь#якорь` или номер), `title`, `relation` (`link`/`mark`), `status` — код из шапки работы, например `accepted` у решения; `depth` в `context`; `code_count` в `targets`; `via` — список целей у `obey` среза работы |
| сигнал | `code` (`null` у открытой работы), `level`, `message`, `target`, `path` и `line`, если есть место |
| понятие | `target`, `title`, `code_count` (мест в коде по проекту) |
| выдержка | `text`, `lines`, `cut` |

В [срезе по диффу](slice-diff.md#json) `matched_targets` перечисляет все совпавшие цели каждого места в коде и тестах, включая точки входа.

У связей «Refines» значение `relation` — `link`; цель решения —
канонический номер, например `ADR-001` для файла `0001-….md`.

Добавить ключ — совместимо. Удалить или поменять смысл ключа — новый номер
`schema` и мажорный выпуск lipi.

## Роли кода <a id="roles"></a>

После правки формата команда `lipi slice docs/export.md#row --role consumes`
найдёт код, который его читает. В выдаче также останутся адреса, где роль
пропущена или записана с ошибкой. Фильтр `--role produces` находит код,
который формирует результат. У каждой связи своя роль. Одна функция может
читать один формат и записывать другой. [Синтаксис меток](rules.md#trace-roles).

В блоках `entry` и `code` поле `target_roles` перечисляет совпавшие якоря
и их `roles`, если у одной из совпавших связей указан атрибут роли или задан
`--role`. Пустой список означает, что распознанных значений нет.
При опечатке поле `invalid_roles`
содержит исходное значение. Например, `role=consumes,produce` обозначает
читателя, а второй элемент требует проверки при любом из двух фильтров.
Тестовые места остаются в своём обычном блоке.

В `summary.roles` места считаются после выбора слоёв, до обрезки и только
в прочитанных источниках. При фильтре `matched` — число мест с запрошенной
ролью. `unassigned` — дополнительные места с пропущенной ролью.
`unrecognized` — места с ошибкой в роли, в том числе совпавшие по корректному
значению. Внутри каждого счётчика адрес учитывается один раз. Для внешнего
якоря `target_roles[].target` содержит имя подключения, например
`service::docs/export.md#row`.

Если в файле есть роли или задан `--role`, у связанных понятий в блоке
`concepts` перечислены подходящие объявления файла в поле `locations`,
включая объявления без роли. Адрес объявления под каждым якорем ведёт
к первой строке группы меток. Если список обрезан, `locations_omitted`
показывает, сколько адресов осталось.

Например, `rebuild` потребляет `#row`, а ещё три места ссылаются на
`#row` без роли. При `--role consumes` сводка покажет «1 потребитель ·
ещё 3 места без роли». Проверить стоит все четыре адреса. При `--only code`
из списка исчезнут точки входа, при малом бюджете поместится меньше строк.
Оба числа в сводке сохранятся.
`code_count` отдельного понятия считает связанные с ним места кода, включая
точки входа, до фильтра по роли. Одно место может входить в счётчики двух понятий.

## Поиск в подключённом репозитории <a id="repo-search"></a>

Известную цель можно указать как `core::docs/api.md#request`,
`core::docs/api.md` или `core::ADR-018`. Вызов `lipi slice 'core::выгрузка отчёта'`
ищет только в этом подключении. Действуют [обычные правила поиска](slice.md#target)
в [области чтения](settings.md#repos), включая страницы из `page_dirs`.
Без `lipi.json` у соседа доступны только точные цели `путь.md#якорь`,
без обратных связей.

При `not-found` для местной текстовой фразы lipi предлагает команду для
каждого доступного прямого подключения с `docs` в `read` и собственным
`lipi.json`, в порядке `repos`. Например, для `lipi slice 'выгрузка отчёта'`
подсказкой может быть `lipi slice 'core::выгрузка отчёта'`. Команда сохраняет
исходную фразу. При формировании подсказки поиск у соседа не выполняется,
поэтому команда тоже может вернуть `not-found`.

В JSON ошибки (`schema: 1`) подсказки передаются массивом `suggestions`
с объектами `{repo, command}`. Поле отсутствует при остальных исходах,
включая местную неоднозначность, запрос по адресу или с префиксом репозитория
и промах без подходящих подключений.

При совпадении по заголовку в тексте указаны репозиторий, заголовок, способ
совпадения и путь к файлу относительно каталога запуска. Для страницы
`notes/drafts/export.md` в `../core` из корня потребителя путь будет
`../core/notes/drafts/export.md`, а из `src/` — `../../core/notes/drafts/export.md`.
В JSON из обоих каталогов у цели одинаковые `repo: "core"`,
`target: "notes/drafts/export.md"`, `kind: "page"` и `found: "title"`.
У кандидатов при неоднозначном запросе также есть `repo` и `target`
относительно корня владельца.
