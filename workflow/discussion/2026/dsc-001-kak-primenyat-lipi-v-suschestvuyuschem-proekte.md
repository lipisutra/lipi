# Как применять Lipi в существующем проекте: опыт пилотов

- Created: 2026-11-20
- Updated: 2026-11-20
- Status: open

## Вопрос

Как команде с действующим кодом, документацией и тестами попробовать Lipi
на одной задаче и понять, помог ли он выбрать место правки? Ниже — наблюдения
на Lipi 1.0.1 и рекомендации для следующего пилота. Примеры путей условные.

## С чего начать в одном репозитории

1. Возьмите задачу, по которой есть практический выбор: расширять существующую
   операцию или писать новую, менять обработчик или интерфейс. Запишите вопрос
   словами разработчика до того, как покажете ему готовый якорь.
2. Из корня проекта посмотрите план `lipi init --dry-run`. Выберите существующий
   каталог описания через `--docs`; с теми же аргументами сначала просмотрите
   план, затем примените его командой без `--dry-run`. При собственном формате
   бэклога можно оставить `"workflow": null`. Для уже существующих решений
   в `docs/adr` явно задайте `"decisions": "docs/adr"`. Если важен статус
   решения, проверьте на одном ADR, что Lipi прочитал его английское поле
   `Status`. [Развёртывание](../../../SETUP.md#init)
3. Выполните `lipi check` и один раз сравните с `lipi check --no-baseline`:
   первый запуск мог записать прежние ошибки в базовую линию. Для пилота
   достаточно стандартного `"enforce": false`.
4. Выберите один абзац с проверяемым обещанием и дайте ему явный якорь.
   Поставьте метки на обработчик и на тест, в котором есть утверждение
   именно об этом поведении. В `layers` укажите слои, между которыми предстоит
   выбирать. Оставьте тесты в обходе; для синтетических фикстур используйте
   точный путь, например `tests/fixtures` в `skip_dirs`. [Настройки](../../../docs/ru/settings.md)

## Когда описание и потребитель лежат в разных репозиториях

Пусть рядом лежат два клона, `service/` с описанием и `client/` с обработчиком.
В `client/lipi.json` добавьте подключение к владельцу описания:

```json
{"repos": {"service": {"path": "../service", "read": ["docs"]}}}
```

Теперь у обработчика и у его теста можно поставить метку
`@trace service::docs/api.md#next-page`. Из клиента выполните
`lipi slice 'service::docs/api.md#next-page'`. Чтобы из самого владельца
найти потребителей этого раздела, добавьте в `service/lipi.json` обратное
подключение:

```json
{"repos": {"client": {"path": "../client", "read": ["code", "tests"]}}}
```

Из `service/` проверьте `lipi slice 'docs/api.md#next-page'` и `lipi map`:
видны ли обработчик и тест с именем клиента? В сводке среза посмотрите,
какие источники удалось прочитать. Число проверенных на устаревание мест
относится к локальным парам; для межрепозиторных связей охват указан отдельно.
[Подключения](../../../docs/ru/settings.md#repos) · [Охват среза](../../../docs/ru/slice.md#repos)

## Какие решения помог принять пилот

| Вопрос разработчика | Что показал опыт | Что повторить на своей задаче |
| --- | --- | --- |
| Нужна ли новая операция для показа выбранной записи? | Срез вывел на готовое чтение по ID в одном слое. В другом слое обработчик запрашивал список. | Проследите путь от входа до вывода и назовите первый шаг, где теряется нужное поведение. |
| Ловит ли найденный тест ошибку выбора версии? | При подмене поиска по ID возвратом текущей версии тест сначала проходил: в его данных запрошенная версия оставалась текущей. После разведения версий тест упал именно на значении из другой версии. | В копии проекта прогоните тест до подмены, с подменой и после восстановления. Запишите конкретное упавшее утверждение. |
| Как найти тест изменённого поля ответа? | Общая метка привела к соседнему тесту. После выделения пагинации в отдельный якорь срез по диффу указал на утверждение о признаке следующей страницы. В этом опыте проверили навигацию; сам тест не запускали. | Внесите локальную правку и запустите `lipi slice --diff HEAD`. Откройте указанное место и проверьте, что утверждение читает изменённое поле. |
| Как начать без готовой ссылки? | В трёх задачах полная формулировка не дала первого полезного среза. Короткая фраза из заголовка нашла карточку у владельца; из потребителя та же фраза её не нашла. | Начните с `lipi map` без аргумента, затем попробуйте `lipi slice 'фраза из заголовка'`. Если бэклог лежит вне описания соседа, в 1.0.1 повторите поиск из клона владельца. Предложение для этого случая — [ISS-020](../../issue/2026/iss-020-poisk-po-zagolovkam-v-razreshennyh-katalogah.md). |

В одном опыте перефразирование документации сняло предупреждение об
устаревании, хотя ошибочная подмена в коде сохранилась. Поэтому для ревью
полезно записывать отдельно, куда привёл срез, какое утверждение прочитано
и какой тест действительно запускали. [Как читать места в тестах](../../issue/2026/iss-019-utochnit-v-svodke-sreza-chislo-testovyh.md)

## Как найти непосредственного читателя при изменении ответа

В ответ операции добавили необязательное поле. На одном и том же диффе
сначала нашлись одно понятие и два места в подключённом репозитории. Место,
где клиент разбирает ответ, ревьюер отыскал вручную. Затем одним узким
якорем связали участок, где сервис формирует ответ этой операции, и участок,
где клиент его читает. Строки изменения остались прежними. Теперь
`lipi slice --diff HEAD` показал два понятия и три места.

Полезно открыть из сводки оба среза. Узкий срез ведёт к читателю ответа.
Общий срез сохраняет связь с кодом показа и с обработчиком соседнего
сценария. У последнего есть собственная метка на общую тему; по ней нельзя
сделать вывод, что обработчик получает изменённый ответ. Этих двух срезов
хватило, чтобы разобраться в составе выдачи без поиска по коду.

В выводе ревью оставили две строки:

- Прежний показ совместим с расширенным ответом.
- Новое поле пользователю не показывается.

Для продолжения после перерыва хватило комментария с версиями обоих
репозиториев, выводом по читателю и следующим местом для сверки. Между
подходами код не менялся. Остаётся открытым вопрос, как ревьюер поймёт,
какой вывод пересмотреть после следующей правки договора или читателя.

## Что собрать в следующий раз

Попросить разработчика начать с формулировки задачи без готового пути.
Сохранить стартовый каталог, первые команды, первый полезный результат
и место, которое пришлось искать вручную. Главный вопрос — какое решение
изменилось после чтения найденного кода или теста. По следующим примерам
можно выбрать, что вынести в основной README, а что оставить в руководстве
по развёртыванию и настройке нескольких репозиториев.
