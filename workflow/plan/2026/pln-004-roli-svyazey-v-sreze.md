# Роли связей в срезе

- Created: 2026-11-21
- Updated: 2026-11-21
- Status: in progress

## Purpose

После изменения договора ревьюер может одним срезом найти код, который потребляет результат или формирует его, и увидеть адреса, где автор ещё не указал роль. Роль принадлежит связи между объявлением и конкретным якорем. Основание и пример с функцией `rebuild` — в [ISS-024](../../issue/2026/iss-024-roli-svyazey-mezhdu-kodom-i-dogovorom.md).

## Подход

Сейчас `checker/marks.py` объединяет соседние комментарии перед одним объявлением и сохраняет для цели строку метки. Суффикс `role=…` остаётся в тексте комментария и мешает распознать такую группу. Поэтому сначала расширяем общий разбор, затем передаём роли через локальный и внешний индексы. Текст и JSON используют один отбор мест. Роли автор ставит по необходимости.

## Шаги

### З1. Разбор метки и ошибки в `check`

- Разобрать необязательный суффикс после списка целей. В `@trace docs/export.md#row role=consumes,produces` обе роли относятся к одному якорю. Если целей несколько, роли относятся к каждой. Сохранить строку метки, границы группы и позицию объявления. Для повторной цели объединять роли без повторов, в том числе при соседстве с обычной меткой.
- **T5** сообщает о неверной роли или месте её применения и указывает файл, строку и значение. Проверить пустой и неизвестный аргумент, смешанный список `consumes,reads`, роль в тесте, на `PLN-003` и на `ADR-007`. Для явного якоря внутри ADR действует обычная ролевая метка.
- Уровень T5 по умолчанию — `error`. Как у T1, проект может задать `error`, `warning` или `off` через `codes.T5`. На одной метке с опечаткой проверить ошибку по умолчанию, предупреждение при `warning` и отсутствие находки T5 при `off`. При любом уровне срез сохраняет связь с разрешённым якорем и показывает адрес с подписью «роль не распознана» и исходным значением.
- Адресно проверить соседние и встроенные метки, перестановку строк группы и `lipi: ignore-trace`. Убедиться, что `mv` переписывает только адрес цели, карта считает одну группу один раз, а проверка устаревания определяет ту же область кода, что и срез. Описать синтаксис и T5 в обеих редакциях правил и в поставляемой инструкции по меткам.

### З2. Срез раздела, страницы и файла

- Передать роли через `SliceIndex` и `RepoIndex` по точному адресу владельца и якоря. В JSON схемы 1 запись имеет вид `"target_roles": [{"target":"docs/export.md#row","roles":["consumes"]}]`. Цели сортируются по адресу, роли — в порядке `consumes`, `produces`. Для внешних адресов использовать действующее правило `имя::цель`.
- В обычном срезе и в срезе по изменению включать `target_roles` у места кода или точки входа, если задан `--role` или хотя бы у одной совпавшей связи явно указан атрибут роли, в том числе с опечаткой. Перечислять все совпавшие связи с явными якорями. У связи без роли указать `"roles":[]`. Для `role=reads` указать `"roles":[],"invalid_roles":["reads"]`, для `role=consumes,reads` — `"roles":["consumes"],"invalid_roles":["reads"]`. Поле `invalid_roles` появляется только при ошибке значения. Тестовые места остаются в своём блоке.
- При `--role consumes` сохранять место, если среди совпавших связей есть потребление, связь без указанной роли или связь с нераспознанным значением. Симметрично для `produces`. Например, при потреблении A и отсутствии роли для B видны обе связи одной строкой. При формировании A тот же адрес остаётся для проверки B.
- Проверить смешанный список `role=consumes,produce` с обоими фильтрами. При `--role produces` место остаётся видно с пометкой «роль не распознана». Единственная распознанная роль этой связи — `consumes`.
- В сводке «ещё N мест без роли» считать дополнительные адреса с пропущенной ролью. Адрес с нераспознанным значением учитывать отдельным счётчиком. Если у него также есть запрошенная роль, её показывать, а в общем числе мест адрес считать один раз.
- Роль подписывать в существующих блоках `entry` и `code`. В срезе файла показать у его собственных понятий, какое объявление какую роль имеет; у соседних мест подписывать их собственные связи. Тестовые адреса оставить в их обычной выдаче, вне ролевого подсчёта. Охват — только прочитанные источники и разрешённые области.
- Проверить на функциях из ISS в одном слое. Потребители строки выгрузки дают `rebuild`, а формирующие отчёт — тот же `rebuild` через другую цель. Добавить функцию нормализации с обеими ролями и место без роли. Повторить поиск с одним подключённым потребителем, затем с недоступным источником.
- На проекте без ролевой разметки сверить текст и весь JSON без `--role` с прежним выводом, включая контрольный дифф только кода из PLN-003 на `v1.2.1`. С тем же проектом под `--role consumes` проверить, что у показанного адреса без роли есть запись о цели с `"roles":[]`.
- При `codes.T5: off` сравнить две метки на один якорь перед разными функциями. Одна содержит `role=reads`, вторая оставлена без роли. В обычном срезе и с каждым из двух фильтров текст и JSON показывают оба адреса. В сводке одно место с нераспознанной ролью и одно без роли. У первого в JSON видно значение `reads`.

### З3. Роли в срезе по изменению

- В `--diff` и `--staged` соединять роли только с целями данного изменения. Для сохранившейся или добавленной связи брать роли с новой стороны диффа, для снятой — с прежней. Для живой метки на удалённый якорь брать роль из этой метки. Использовать те же снимки, что и для оснований ISS-023. Поля `via`, `matched_targets` и `reasons` сохраняют свой смысл.
- Проверить пример сначала по JSON. При правке только `#row` у `rebuild` видно потребление. При правке ещё и `#summary` видны обе связи, один адрес и одно место в счёте. Сверить смену роли и удаление метки; в `--staged` неподготовленная правка роли поверх индекса не должна попасть в ответ.

### З4. Сводка, предел вывода и приёмка

- Полный счёт уникальных адресов `entry` и `code` вести после `--layer`, до `--only` и общего предела объёма. В тексте и JSON использовать одинаковый набор показанных адресов и число пропусков. Адреса без роли подчиняются тому же пределу. У `--full` остаётся задача раскрывать выдержки. Охват `checks.staleness` считать до ролевого фильтра.
- Закрепить пример в справке EN/RU и описать изменение в открытой записи CHANGELOG. При одном потребителе и трёх дополнительных местах без роли оба языка и JSON должны дать числа 1 и 3. Малый бюджет сокращает адреса. При `--only code` скрывается блок точек входа. В обоих случаях счёт сохраняется. Группировка карты по ролям и роли на номере решения целиком остаются за пределами ISS.

## Completion criteria

По одному срезу ревьюер может открыть потребителей изменённого договора и оставшиеся места без роли. На примере `rebuild` текст и JSON согласованы для раздела, страницы, файла и диффа. По шагам достаточно адресных тестов. Перед приёмкой — полный локальный набор на английском и русском, затем `lipi check` и `lipi audit`. Выпуск 1.3.0 остаётся отдельным решением после приёмки.

## Результат З1

Общий разбор сохраняет для каждой цели группы распознанные роли и исходные ошибочные значения. На примере `role=consumes,produce` проверены все три уровня T5. При каждом уровне связь видна в графе. После `lipi mv --apply` адрес ведёт к перенесённому разделу, суффикс сохранён побайтно, обычный срез находит функцию. Видимость по обоим ролевым фильтрам проверяется в З2.

Карта считает группу один раз на цель. При правке тела функции T2, аудит A4 и срез учитывают оба связанных раздела. Синтаксис описан на двух языках, поставляемая инструкция применена к самому lipi. Исключение для ошибки T5 в линии 1.x записано в [ADR-022](../../adr/adr-022-oshibka-po-umolchaniyu-dlya-yavno-ukazannoy.md).

## Результат З2

В срезе раздела `rebuild` найден по `--role consumes` для `#row` и по `--role produces` для `#summary`. Срез страницы сохраняет у одного адреса разные роли по целям, а срез файла показывает его собственные метки у соответствующих понятий. При отключённом T5 опечатка `produce` остаётся видна по обоим фильтрам. Места с пропущенной ролью и с опечаткой различимы в тексте и JSON.

Проверены выбор слоя, подключённый потребитель и недоступный сосед. На проекте без ролей сверены пять запросов с CLI из тега `v1.2.1`: раздел, страница, файл, `--diff HEAD` и `--staged` с правкой только тела функции. На обоих языках текст совпал побайтно, JSON — по всем полям.

По замечанию при проверке З2 добавлен пример с несколькими объявлениями в одном файле. У `rebuild` один адрес под обоими якорями — начало группы меток. Самостоятельное объявление `plain` видно с подписью «без роли». Сводка поясняет, сколько точек входа входит в общее число мест в коде.
