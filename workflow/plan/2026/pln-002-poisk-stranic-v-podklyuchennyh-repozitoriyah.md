# Поиск страниц в подключённых репозиториях

- Created: 2026-11-20
- Updated: 2026-11-20
- Status: completed
- Closed: 2026-11-20
- Result: В Lipi 1.1.0 добавлены каталоги страниц подключений, команды поиска в тексте и JSON и путь для открытия найденного файла из каталога запуска.

## Purpose

Дать разработчику путь от слов из заголовка до файла у соседа, даже если
он начинает в подкаталоге потребителя, а карточки ведутся в обычном Markdown.
Договор поиска и пример двух репозиториев записаны в [ISS-020](../../issue/2026/iss-020-poisk-po-zagolovkam-v-razreshennyh-katalogah.md).

## Подход

Расширить область страниц существующего подключения. Для запроса
`имя::фраза` использовать действующий поиск заголовков и его порядок кандидатов.
Результат 1.0.1 служит контрольным примером: заголовок в обычном `docs/`
уже находится без дополнительных настроек. Все примеры для проверок синтетические.

## Шаги

### З1. Настройка и границы области чтения

- Расширить проверку конфигурации подключения и модель источника полем
  `repos.<имя>.page_dirs`. Каталоги задаёт потребитель от корня соседа.
  Поле требует `docs` в `read`; при его отсутствии выдать C1 даже для пустого списка.
- Проверить C1 для неверного типа, пустого элемента, абсолютного пути,
  выхода за корень (в том числе через символьную ссылку) и повторного
  разрешённого пути. Совпадение с каталогом описания и вложенные каталоги
  допустимы. У источника сохраняются обычные исключения Git, архива и
  `skip_dirs`; решения сохраняют свою область `decisions`.
- Расширить область `docs` для всех команд, читающих соседа. На одной странице
  проверить метку из кода потребителя через `check`, строку по этой метке
  в `map` и поиск по заголовку через `slice`.
- Вместе с поведением обновить описание настроек на двух языках. Для
  совместимого расширения запланировать 1.1.0 и указать в CHANGELOG,
  что перед добавлением ключа требуется обновить программу.

### З2. Поиск и адрес результата

- Включить дополнительные страницы в существующий индекс названного
  соседа. На фикстуре проверить поиск по заголовку, чтение найденной страницы
  и отсутствие дубликатов при пересечении каталогов.
- Проверить одно, несколько и ноль совпадений: коды 0/1, `found: title`,
  `ambiguous`, предел в пять кандидатов, порядок и `not-found`.
  В JSON сохранить схему 1 и пару `repo` + `target` относительно владельца.
  В тексте вывести владельца, заголовок, причину совпадения и путь,
  который можно открыть из каталога запуска.
- Повторить контрольный пример без `page_dirs`. У соседа без `lipi.json`
  проверить отказ поиска по фразе и успешное открытие явного якоря.
  Сверить поведение с описанием среза в обеих редакциях.

### З3. Подсказка при локальном промахе

- При `not-found` для местной текстовой фразы вывести готовую команду
  для каждого доступного соседа с конфигурацией и областью `docs`.
  Сохранить порядок `repos` и исходную фразу, включая пробелы и кавычки.
  Использовать сведения о подключениях без пробного поиска совпадений.
- В ответ `not-found` схемы 1 добавить необязательный массив `suggestions`.
  Пример элемента: `{"repo":"neighbor","command":"lipi slice 'neighbor::выгрузка отчёта'"}`.
  Текст и JSON используют один список. Когда предложить нечего, поле отсутствует.
  Коды выхода, `error` и `candidates` сохраняются.
- Проверить две подсказки, включая соседа без совпадения. Проверить отсутствие
  подсказки при местном успехе, неоднозначности, явном внешнем запросе,
  запросе по пути и отсутствии подходящих подключений. Добавить сообщения
  и пример вызова в английскую и русскую редакции.

## Completion criteria

- На временном проекте с `workflow: null` пройти путь из ISS-020 через CLI:

  Из корня открыть `../neighbor/notes/drafts/export.md`, из `src/` —
  `../../neighbor/notes/drafts/export.md`. Сверить содержимое с исходной

- Обычный поиск в каталоге описания проходит и без нового поля.
  Страница вне объявленных областей недоступна. На двух языках коды
  выхода и машинные адреса совпадают.
- По шагам проходят адресные тесты, в конце — полный локальный набор,
  `lipi check` и `lipi audit`. В итог плана записать результаты сквозной
  проверки из корня и из подкаталога.

## Проверка на временных репозиториях

В двух соседних клонах с `workflow: null` запрос «выгрузка отчёта» дал
локальный `not-found`. Команда из `suggestions` нашла страницу в
`notes/drafts/` по заголовку. Из корня путь `../neighbor/notes/drafts/export.md`
и из `src/` путь `../../neighbor/notes/drafts/export.md` открыли один файл.
На английском и русском JSON совпал, включая адрес
`{"repo":"neighbor","target":"notes/drafts/export.md"}`.
Когда одна фраза встретилась в семи заголовках, из обоих каталогов пришли
одни и те же первые пять кандидатов в порядке пути.

Метка потребителя на якорь той же страницы прошла `check`; `map` показал
одно место в коде у внешней цели. При замене `read` на `["tests"]`
с сохранением `page_dirs` команда `check` вернула C1 и код 2.

Локальный полный прогон прошёл (1108 тестов); добавленный во время прогона
1109-й тест проверяет архив решений за символьной ссылкой и прошёл отдельно.
На большой фикстуре с тремя репозиториями срез занял 1,256 с, карта — 1,121 с.

## Проверка в пилоте

2026-11-20 разработчик проверил кандидат 1.1.0 на существующей задаче.
Потребитель подключил каталог карточек соседа через `page_dirs` при `docs` в
`read`. Из корня потребителя и из `src/` одна и та же фраза дала `not-found`
с кодом 1 и одинаковую команду в `suggestions`. Оба запуска этой команды
завершились с кодом 0. Разработчик открыл оба пути из строки «Открыть» и
подтвердил, что это нужная карточка. В JSON `target.repo` и `target.target`
совпали из обоих каталогов.
